Firmware security · explained from scratch

Does the chip actually run the code the “ingredients list” says it does?

No firmware background needed. We’ll build up from “what is firmware” to a real security check — and why it catches an attack that the usual check misses.

Firmware in 90 seconds

Six ideas. Everything after this is built from them — read these and the rest reads easily.

Firmware

The lowest-level software baked into a device — it runs before the operating system and starts the machine up. On a PC this is the UEFI firmware (the modern BIOS). Like the building’s wiring: it’s there before anyone moves in.

Module

Firmware isn’t one program — it’s a bundle of small programs (drivers, services), each called a module. A firmware image contains dozens to hundreds. Think apps on a phone — but for the chip.

Firmware image .fd

The single file that gets written (“flashed”) onto the chip — all the modules packed together into one blob. Our example file is OVMF.fd. One shipping container holding every module.

Module ID GUID

Every module carries a unique ID — a GUID, like 2ec9da37-…. It identifies which module something is. A serial number, or a name badge.

Fingerprint SHA-256

A hash is a short fingerprint of a file’s exact bytes. Change a single bit and the fingerprint changes completely. So two files with the same fingerprint are byte-for-byte identical. A wax seal that shatters if touched.

Ingredients list SBOM

A SBOM is a signed inventory produced when the firmware is built: every module, its ID, and its fingerprint. The recipe card that says exactly what should be inside.

The whole point, with a real example

THE ATTACK — a “same-ID swap”

An attacker rips out the real SecurityModule and drops in malware — but keeps the same ID (e5f6…) so the inventory still looks right. Only the actual bytes changed, so its real fingerprint is now different.

✓ Membership check — the usual one
“Are IDs a1b2, c3d4 and e5f6 all present?”
→ YES. PASS. ✓
Fooled. The trojan kept the ID, so the inventory looks complete. This is what most tools do — check the names, not the contents.
✗ Byte-integrity check — what we built
“Does e5f6’s real fingerprint equal the declared 71a4?”
→ dead… ≠ 71a4. FAIL. ✗
Caught. The bytes don’t match the fingerprint the SBOM promised — so the module is not genuine, whatever its ID says. The release is blocked.
IN ONE LINE  Membership asks “is the right name on the list?” Byte-integrity asks “is it really that module, or an impostor wearing its badge?”

How we actually check it

The declared fingerprint comes from the SBOM. The real one we compute ourselves from the shipped image — then compare.

build → SBOMgives declared fingerprint shipped OVMF.fd→ unpack the image→ find the module→ read its code bytes→ fingerprint it

Unpacking means opening the container: a firmware image holds FV regions → each holds FFS files (one per module) → inside is the actual program, a PE32 section. Image → drawers → folders → the document. We pull the document’s bytes and fingerprint them.

Phase 1Prove it works — on one kind of module

Firmware modules run at different stages of boot; each stage stores modules a bit differently. We started with the biggest group: DXE drivers (the “main” stage).

  1. Take the declared module the build produced (AmdSevDxe).
  2. Take the real bytes of that module out of the shipped OVMF.fd.
  3. Fingerprint both. For 5 out of 5 DXE drivers they were identical.
  4. Flip one bit of the shipped module → fingerprints diverge → the swap is DETECTED.
FINDING  For this stage the two sides line up directly — no adjustment needed. (An earlier report had claimed a mismatch; it turned out to be reading the wrong bytes. Fixed.)

Phase 2Turn it into a real gate — honestly

We made byte-integrity a hard release check and ran it over every module in the image. That immediately taught us something.

THE HONEST CATCH  A first run called those 11 “modified” — false alarms. They’re all early-boot modules (the PEI / SEC stages) that legitimately look different in the image. So the tool reports them as “needs a fair-comparison step,” never as tampered — a clean image reads clean, and the number stays truthful.

Phase 3The last 11 — make the comparison fair

Why do early-boot modules look different? When a module is fixed into a specific spot in the chip, all its internal addresses get shifted — called rebasing. Same code, shifted numbers.

Only the base address differs. Placing the module in the chip added a fixed offset to every internal pointer. The image tracks exactly which bytes were shifted (a “relocation” list), so the change is perfectly reversible.

The fair-comparison step (“canonicalization”) simply subtracts that offset back out — returning the shipped module to its declared form before we fingerprint it. Like translating two documents into the same language before comparing them.

Glossary — every term used here

Firmware

Low-level software baked into a chip that runs before the operating system and boots the machine.

UEFI / BIOS

UEFI is the modern PC firmware standard; BIOS is its older name. They do the same job: start the computer.

edk2 / OVMF

edk2 is the open-source toolkit UEFI firmware is built from; OVMF is an open UEFI firmware we use as the test target.

Module

One small program inside the firmware (a driver or service). Firmware is a bundle of many modules.

Firmware image .fd

The single binary file flashed onto the chip, containing all modules packed together (e.g. OVMF.fd).

GUID

Globally Unique Identifier — a 128-bit label that says which module something is. A serial number / name badge.

Hash SHA-256

A fingerprint of a file’s exact bytes; changing one bit changes it completely. Same hash ⇒ identical files.

SBOM

Software Bill of Materials — a signed inventory made at build time: every module, its GUID, and its hash.

Membership check

Confirms every declared module (by GUID) is present. Doesn’t look at the bytes.

Byte-integrity

Confirms each module’s shipped bytes match the hash the SBOM declared — catches a same-GUID swap.

Same-GUID trojan

An attack that replaces a module’s code but keeps its GUID, so the inventory still looks correct.

FV / FFS / PE32

The image’s nested containers: Firmware Volume → Firmware File (one per module) → PE32 section (the actual code). Drawers → folders → document.

Boot stages SEC · PEI · DXE

Firmware boots in phases: SEC (first), PEI (early init), DXE (main, most drivers). Modules belong to a stage.

Rebase / relocation

Adjusting a module’s internal addresses when it’s placed at a fixed spot in the chip. The image records exactly what shifted, so it’s reversible.

Canonicalization

Converting both sides to the same standard form (here: undoing the rebase) so a byte comparison is fair.

GenFw

The edk2 build tool that normalizes a module (zeroes timestamps, etc.) as it assembles the image.

SI-7(1)

A security control (“integrity checks over components”). Byte-integrity is what makes it mean “the bytes match,” not just “a hash exists.”

Honest scope

Coverage is always reported: modules that can’t yet be byte-checked are labelled needs-canonicalization, never silently skipped and never mislabelled “tampered.” Declared hashes come from the build-time SBOM; observed bytes come from the shipped image — two independent sources, one comparison.
