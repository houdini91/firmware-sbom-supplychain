Design exploration · oss-lane compliance gate

Making the gate speak each framework's language

A control catalog so every rule carries a description and renders in the target framework's own words — right-sized against what the gate already does and where the signed-verdict format is heading.

planning/framework-aware-output-design.html · companion to A2-A4-PLAN.md & FRAMEWORKS.md

Bottom line up front. Do the Minimal version now: add a description and a per-framework citation to each control in frameworks.yaml (which is already framework-partitioned), flow those into the signed verdict's controlAssessments[], and derive the rego per-report controls tags from that catalog instead of hand-maintaining a second, drifting copy. Add one cheap forward-compatible seam — an optional canonical/openCre key per control — so this grows into a canonical catalog or into CDXA without a rewrite. Do not build a standalone canonical catalog (Moderate) as its own layer, and do not adopt CDXA (Full) yet — both should wait on the A2-A4 verdict-format decision, where CDXA is already the leading candidate. Detail and justification below.

1 · The problem, concretely

The gate should reflect the controls and frameworks it is set up to cover. Three asks, from the project owner:

  1. each control should expose its description — what the control actually means;
  2. the gate's output should match the target framework's own language — not a generic string, but phrasing and citation that read as NIST vs. S2C2F vs. CRA;
  3. because many frameworks reuse the same underlying check, a control should be defined once and referenced by many frameworks — not copy-pasted per framework.

Take one real rule that is enforced today: component-byte-integrity — the check that the shipped PE32 bytes of every hashable module match the SBOM's declared hash (the one that catches a same-GUID trojan swap). That single check is claimed against several controls across several frameworks, each of which describes it in its own words:

FrameworkControlHow that framework phrases the ask
NIST 800-53SI-7(1) Integrity Checks "The information system performs an integrity check of [software, firmware, information]…"
NIST 800-53 / 800-161SR-4(3) Validate as Genuine & Not Altered "Employ [controls] to validate that the component received is genuine and has not been altered."
OpenSSF S2C2FAUD-3 "Validate integrity of the OSS that you consume into your build."
CISA 2026 / BSI TR-03183-2Component Hash · §5.2.2 "Cryptographic hash of the deployable component" (SHA-512 tier for BSI).

One check, four to five framework "renderings," each wanting its own reference number and sentence. That is the shape the output should take — and the reuse the data model should capture once.

2 · Current state — and its honest limitation

Two separate places encode "which control does this satisfy," and neither carries a description or framework language:

a. Hard-coded messages + bare control tags in the rego

Each of the 19 verifier_reports is built by _report(name, ok, pass_msg, fail_msg, controls). The messages are fixed English strings and the controls field is an array of bare id strings:

_report(
    "component-byte-integrity", _byte_integrity_ok,
    "shipped module bytes match the SBOM's declared hash (byte-integrity — detects a same-GUID swap)",
    _byte_integrity_msg,
    ["SI-7(1)", "SR-4(3)", "S2C2F-AUD-3"],   // <- free strings, no description, no citation
),

The tag "SI-7(1)" tells a reader nothing about what SI-7(1) is, and the pass/fail message is a generic sentence — not NIST's language, not S2C2F's.

b. The initiative manifest (frameworks.yaml)

The declarative layer is already framework-partitioned and already models rule-reuse correctly — one report name is referenced from many controls' satisfied_by:

sp-800-53:
  controls:
    - id: SI-7(1)
      name: "Integrity checks over components"
      satisfied_by: [component-integrity, component-byte-integrity]
    - id: SR-4(3)
      name: "Validate genuine and not altered"
      satisfied_by: [..., component-byte-integrity]

Controls have id, a short name, and satisfied_by — but no description and no per-framework citation/quote. The rego control_assessments rule already walks this manifest and emits OSCAL-shaped findings (framework, controlId, name, status), so a description added here would flow straight into the signed verdict.

Finding — two vocabularies that have already drifted. The rego controls tags and the frameworks.yaml control ids are maintained independently and use different conventions ("CRA-AnnexI-1" vs. cra-annex-I-II-1; "CISA-2026-hash" vs. cisa-hash). They have already diverged: the rego tags component-byte-integrity with "S2C2F-AUD-3", but the s2c2f block in frameworks.yaml defines only SCA-1, SCA-2, and REB-3 — there is no AUD-3 control there at all. FRAMEWORKS.md even concedes the rego tags are "a representative subset, not the exhaustive mapping." So today there is no single source of truth that a machine can render: the meaning and the framework wording live only in FRAMEWORKS.md prose.

The limitation in one sentence: the gate's machine output can tell you a control passed or failed, but not what it means or how its owning framework phrases it — because descriptions and framework language exist only as human prose, disconnected from the two id vocabularies the gate actually emits.

3 · How mature systems model "one control, many frameworks"

This is a solved problem, and every mature approach lands on the same shape: a canonical requirement defined once, referenced by many frameworks, each with its own citation — a star topology, not per-framework duplication.

SystemModelTakeaway for us
OpenCRE (OWASP) Each standard section links to a shared Common Requirement; a star topology plus transitivity (A→CRE, B→CRE ⇒ A↔B) yields all cross-mappings. The canonical-node idea in its purest form. And it is the linking layer CDXA already embeds.
NIST OSCAL mapping model A machine-readable mapping layer expressing many-to-many control relations (equivalent-to, subset-of, intersects-with) across catalogs "without restating or duplicating the source control content." Our verdict is already OSCAL-Assessment-Results-shaped; OSCAL is the NIST-native fit and keeps the crosswalk as data, not prose.
Secure Controls Framework (SCF) A "Rosetta Stone" metaframework: ~1,500 common controls mapped to 200+ laws/frameworks via a rigorous Set-Theory Relationship Mapping — "implement once, comply many times." Validates the direction, but its scale is the over-engineering warning: we have 6 frameworks, not 200.
CycloneDX CDXA definitions.standards[].requirements[]: each requirement has identifier, title, text, descriptions[], and an openCre[] array for cross-standard linking. Claims bind evidence → requirement. A catalog with per-requirement descriptions and cross-mapping is already what CDXA gives — and it is the leading A2-A4 verdict-format candidate and pairs with our CycloneDX SBOM.
valint / Scribe A declarative initiative file maps framework guidelines → controls → executable rules (uses: rule@v1); output is a signed SARIF report where each rule carries an id + shortDescription. The pattern this repo already adopted. The natural next step is to give those controls the description + framework text the SARIF/verdict can surface.

The standard pattern: define the requirement once (id + description), let each framework reference it with a framework-specific citation and quoted text, and keep the rule→requirement binding separate (many rules can satisfy one requirement; one rule can satisfy many). Our frameworks.yaml already does the rule-binding half well — the gap is purely the description + citation half.

4 · The proposed data model

A rule is the reusable atom. It flows to a control that owns the description, and that control is rendered into whichever framework(s) reference it — each rendering carrying its own citation and language:

One real check → one canonical control that owns the description → many framework renderings, each with its own citation and language. The description is written once; only the citation differs per framework.

6 · Recommendation

Do Minimal (a) now. Build the seam toward Full (c). Skip Moderate (b) as a standalone step.

The reasoning, honestly:

  • The reuse problem is already ~80% solved. The reusable atom the owner is worried about is the rule, and frameworks.yaml already references one report from many controls' satisfied_by. What is genuinely missing is only the description and the per-framework citation — which is exactly, and only, the Minimal option.
  • The manifest is already framework-partitioned, so per-framework language has a natural home (one citation block per control). No new indirection is needed to get NIST-vs-S2C2F wording into the output.
  • Minimal also fixes a real bug, not just cosmetics: deriving the rego controls tags from frameworks.yaml kills the two-vocabulary drift (the missing-AUD-3 mismatch above) and makes the manifest the single source of truth the signed verdict renders from.
  • Moderate is ceremony without proportionate payoff today. A canonical catalog + crosswalk + resolver is the correct pattern (OSCAL, SCF, OpenCRE all use it) — but it earns its keep at scale (SCF does it for 200+ frameworks). At 6 frameworks / ~27 controls / 19 rules, the description duplication it removes is a handful of lines, and it adds an indirection layer and resolver code. Build it only if the framework count grows materially or a control's description genuinely needs to diverge from a copy — not preemptively.
  • Full is the right destination, but it is gated on a decision that is still open. A2-A4 is actively choosing the signed-verdict format, with CDXA a leading candidate precisely because its requirements[] already give per-requirement descriptions + OpenCRE cross-mapping — i.e. a control catalog is largely what CDXA hands you for free. Standing up a bespoke canonical catalog (Moderate) now, only to discard it when CDXA lands, is wasted motion. If you invest past Minimal, invest in CDXA — once A2-A4 picks it.
  • So make Minimal a down-payment on Full, not a detour. Choose field names that map 1:1 onto CDXA (description→descriptions[], citation.text→requirement text, id→identifier), and add one cheap optional key now — canonical (or openCre) per control. That single field captures the "these are the same underlying requirement" crosswalk as data immediately, at almost no cost, and is the exact seam that lets you grow into Moderate's resolver or Full's CDXA openCre[] later without re-touching every control.

What "not yet" applies to: not the whole idea — the description + framework language is worth doing now and is cheap. It is specifically the canonical-catalog machinery (Moderate) and the CDXA migration (Full) that should wait: the first on evidence of scale, the second on the A2-A4 format decision.

7 · Data-model sketch (recommended option)

Keep the existing framework-partitioned layout of frameworks.yaml; enrich each control in place. Nothing about satisfied_by or the downstream control_assessments / verify-initiative.py iteration changes shape — they gain fields, they don't restructure.

sp-800-53:
  name: "NIST SP 800-53 Rev 5 (SR/SI/CM/RA)"
  help: https://csf.tools/reference/nist-sp-800-53/r5/
  controls:
    - id: SI-7(1)
      name: "Integrity checks over components"
      # NEW — defined once, the meaning of the control:
      description: >
        Perform integrity verification of software/firmware components to detect
        unauthorized change. Here: every hashable module carries a verified hash
        and its shipped bytes match the SBOM's declared hash.
      # NEW — the framework's OWN language + a real citation (renders in output):
      citation:
        ref:  "NIST SP 800-53 Rev 5 — SI-7(1) Integrity Checks"
        text: "The information system performs an integrity check of [software,
                firmware, information] at [defined transitional states]."
        url:  https://csf.tools/reference/nist-sp-800-53/r5/si/si-7/si-7-1/
      # NEW — the forward-compatible seam (maps to OpenCRE / CDXA openCre[] later):
      canonical: component-integrity-check
      # UNCHANGED — the rule-reuse this file already models correctly:
      satisfied_by: [component-integrity, component-byte-integrity]

s2c2f:
  name: "OpenSSF S2C2F v2"
  controls:
    - id: AUD-3                       # <- add the control the rego tag already referenced
      name: "Validate integrity of OSS consumed into the build"
      description: >
        Validate that the open-source components pulled into the build have not
        been altered — byte-level integrity of each consumed module.
      citation:
        ref:  "OpenSSF S2C2F v2 — AUD-3"
        text: "Validate integrity of the OSS that you consume into your build."
        url:  https://github.com/ossf/s2c2f
      canonical: component-integrity-check   # <- SAME canonical id => the crosswalk, as data
      satisfied_by: [component-byte-integrity]

Two controls in two frameworks now share canonical: component-integrity-check. Today a reader (or a diff, or a coverage report) can already see they are the same underlying requirement rendered two ways. Tomorrow a resolver (Moderate) or CDXA's openCre[] (Full) reads that same field — no re-modeling.

The emitted finding grows correspondingly (illustrative controlAssessments[] entry):

{
  "framework": "sp-800-53",
  "controlId": "SI-7(1)",
  "name": "Integrity checks over components",
  "description": "Perform integrity verification of software/firmware components…",
  "citation": {
    "ref":  "NIST SP 800-53 Rev 5 — SI-7(1) Integrity Checks",
    "text": "The information system performs an integrity check of [software, firmware…]",
    "url":  "https://csf.tools/reference/nist-sp-800-53/r5/si/si-7/si-7-1/"
  },
  "canonical": "component-integrity-check",
  "status": "satisfied",
  "relatedObservations": ["component-integrity", "component-byte-integrity"]
}

Concrete change points (all small)

  • oss-lane/initiatives/frameworks.yaml — add description, citation, canonical per control; add the missing S2C2F AUD-3 control.
  • oss-lane/policy/firmware.rego — control_assessments (~L537): carry description/citation/canonical into each finding. Optionally replace the hand-written _report(..., controls) tag arrays with a derived lookup that inverts satisfied_by, so the tags can no longer drift.
  • oss-lane/verify-initiative.py — print the description/citation.ref alongside each control row (purely additive to the existing reporter).
  • Regenerate oss-lane/policy/initiatives.json and update the sync test fixture.
